# Vegas Poker Planner

Source-first Las Vegas Strip poker trip planner. The canonical GitHub Pages dashboard is in [`site/`](site/) and is
the only directory published by the Pages workflow.

**Published URL.** `https://karagemop466-tech.github.io/Poker3/` serves `site/`. The repository root's
`index.html` is a redirect into `site/`, because the Pages source is still the legacy `main /` setting
(the token used by the integration session cannot change it: `PUT /pages` returns 403) and GitHub's own
branch build would otherwise republish whatever sits at the root after every push. `.github/workflows/pages.yml`
re-deploys the `site/` artifact after that branch build finishes, so the serving copy is the verified
dashboard either way. See flag F29 on the Flagged for review page.

## Evidence policy

Only official venue and property pages and official PDFs substantiate a value. A structure sheet that prints one buy-in,
one start flight and no re-entry, rebuy, add-on or second-flight clause is **sheet-screened only**: it does not prove a
maximum number of entries per player, so no candidate is treated as strictly eligible until the venue confirms the
one-entry, no-rebuy and no-add-on rules in writing (flag F31). Each row carries the exact excerpt, source and retrieval
date. A row with a blank fee or guarantee is always explained by a note or a flag. Guaranteed-pool ÷ entry-fee is
descriptive, never a forecast. Walking minutes are Google Maps estimates, because no venue publishes a walking time.

Values were first read on **2026-11-16**. On **2026-11-17** the official pages and PDFs behind the trip window were
re-read: the DeepStack Extravaganza IV schedule, the seven structure sheets the day plan relies on (1, 5, 6, 7, 11, 17,
22, 26), the Venetian poker-suite rate page, resort-fee page and hotel terms, and the Wynn resort policy page. The
Bellagio weekly PDFs, the Wynn daily and WPT PDFs and the remaining WPT structure sections were not re-read that day;
each row carries its own read and verified dates rather than one blanket claim (see question Q10).
Both dates are carried on every row: `lastChecked` is when the value was read, `lastVerified` is when it was last
confirmed still true. All 52 structure sheets (37 DeepStack Extravaganza IV + 15 DeepStack NYE) have been read in full.

## Scheduled checks

`.github/workflows/checks.yml` is the single scheduled job that reviews official sources at 12:10 UTC
(04:10 PST / 05:10 PDT, the morning pull) and can be dispatched by hand. It also carries a push trigger on its own
file and on the two recorder scripts, so a change to the monitoring setup runs the job immediately instead of waiting
for the cron (a change to one workflow file cannot trigger a different workflow — the earlier attempt routed this
through `source-monitor.yml`, which only starts the poker3 companion monitor). It runs two recorders in order:

- `scripts/check_sources.py` fetches every official URL behind the dashboard. HTML is compared on normalized text;
  PDFs are compared on **all response bytes**, including compressed streams, using SHA-256. PDF-byte changes may be
  metadata-only and require review; they are not proof of changed wording. A URL it cannot reach is recorded as
  `unavailable`, never as "changed". The `textHash` field is retained for compatibility but contains the complete-byte
  digest for a PDF; each row's `hashBasis` / `comparisonKind` identifies its method.
- **2026-11-19 monitoring correction:** the earlier PDF normalizer removed streams rather than extracting their text,
  so its historical `changed: false` / `wordingChanged: false` results do not establish unchanged PDF rules or values.
  The fix reuses the already-recorded raw `hash` as the PDF baseline, so the first corrected run can detect a change
  without a blind reset. It does not retroactively re-verify any event. See
  [`research/pdf-monitor-2026-11-19.md`](research/pdf-monitor-2026-11-19.md) and the site's Flagged for review page.
- `scripts/verify_transcription.py` re-checks the 44 transcribed series-PDF rows against the published data and writes the
  result beside the URL record.

Neither script changes a tournament value on its own: a changed page is re-read by a human first. Both results are
published as `site/checks.json` and shown on the sources page, and the URL recorder creates the file if it does not exist,
so a single unreachable PDF can never abort the run.
- `scripts/daily_feed.py` pulls the schedule page of each Strip poker room and writes a dated snapshot under
  `site/feed/`, so a morning run can be compared with the previous morning instead of replacing it.
- The job then rebases onto `origin/main` and pushes, retrying up to eight times. If all attempts fail it emits a
  warning; the next scheduled run regenerates the observations. A green fetch job alone does not prove publication.

It replaces three overlapping committers (`monitor.yml`, `daily-check.yml` and an earlier version of this one) that
ran on separate crons under separate concurrency groups and overwrote each other; none of the three had ever produced
a run. `source-monitor.yml` shares the same concurrency group so the two jobs are serialised. Flag F30 records this.

Unit tests in `tests/test_integrity.py` assert the arithmetic a reader acts on — the dated quote's two nights
reconciling to the printed total, the `$197.28` nightly floor, `ratio = guarantee / buy-in` on every row, a
`lastChecked` date on every row — and `verify.yml` runs them, so a later edit cannot quietly reintroduce a wrong
number.

The job also starts on a `push` to `main` that touches the workflow, the recorder scripts, the data modules or
`site/data.json`, as well as on the daily cron. `site/checks.json` and `site/feed/**` are deliberately left out of
the trigger, because the job writes them and would otherwise set itself off.

`scripts/audit_951cd431.py` is a second, independent auditor that also runs in `verify.yml`. It re-derives every
one of those numbers straight from `site/data.json` and the verbatim official copies in `raw/`, and deliberately
does **not** import the builder, so a defect in the builder cannot hide itself from the check. It also re-parses
all 94 official DeepStack Extravaganza IV rows and matches them on date and start time.

## Resumption rows

45 rows are resumptions of a field that closed on an earlier day — Day 2 to Day 5 restarts and streamed final
tables at the Venetian and at Wynn. Those rows carry **no** late-registration cut-off and **no** estimated
finish, because the structure sheet's late-registration clause and the session length derived from it describe the
earlier day's flight, not the restart: registration closed when that day ended, and no venue publishes a restart
finish time. The reason is printed on each row and recorded on the Flagged for review page. Resumption rows are
also excluded from the day plan and from the overlap check, so the plan is unaffected.

## Late-registration clauses that cover two start times

Three NYE sheets print one late-registration clause with two clock times, for example
"6 levels + break (~5:25 PM or ~8:25 PM)", because a single sheet covers more than one start flight. The builder
takes the earliest printed time that still falls after a row's own start, so the 3:10 PM row keeps 5:25 PM and the
6:10 PM row takes 8:25 PM. Both times are printed on the sheet, so this disambiguates published values rather than
inventing one; where no printed time falls after a row's start, no cut-off is published at all. This is recorded
on the Flagged for review page.
