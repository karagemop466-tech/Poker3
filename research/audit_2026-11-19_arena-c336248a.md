## 2. Defect found and fixed: the scheduled re-check threw away its own record (F111)

Read from the Actions API, not from the site. Run
[44482186623](https://github.com/karagemop466-tech/Poker3/actions/runs/44482186623) is the scheduled
job for merge commit `5f001742`. Per-step conclusions:

| # | Step | Conclusion |
|---|---|---|
| 5 | Re-check every official URL behind the dashboard | success |
| 6 | Re-check the transcribed series-PDF rows | success |
| 7 | Fetch the morning daily schedule feed | success |
| 8 | **Verify the dashboard still passes its own checks** | **failure** |
| 9 | Record the check results on the main branch | **skipped** |
| 10 | Push the record to main | **skipped** |

`check_sources.py` had already written a correct observation of 108 official URLs to disk. The job
then failed, the two publish steps were skipped, and the published `site/checks.json` kept its
07:34:30 UTC state. The failure left no explanatory log line; the only annotation is
"Process completed with exit code 1".

Two independent causes, both reproduced in a scratch copy of the repo:

1. **No `if: always()`.** Any failing step above the publish steps suppresses the record.
2. **A test treated a changed source as a build error.** `tests/test_index_evidence_labels.py`
   asserted `record["changed"] is False` for the seven primary structure sheets. Reproduced by
   setting `changed: true` on `dse_nov_2026-structure_6.pdf`: exactly one test fails
   (`test_recheck_record_actually_supports_the_date`) and nothing else. A changed source is the
   thing this monitor exists to surface; the same run had already recorded two changed Wynn
   booking-engine URLs at 07:34 UTC.

**Fix.** The dashboard check now carries `continue-on-error: true` and an id; both publish steps
carry `if: always()`; a final step re-raises the failure with
`if: steps.dashboard.outcome == 'failure'`. The record is always published and a broken dashboard
still shows as a red run. The test now asserts that the date on the landing page is backed by a
row that was actually fetched (HTTP 2xx, real ISO timestamp) rather than by an unchanged row;
whether the bytes moved is reported on the Sources and Flagged pages. Four new assertions in
`tests/test_workflows.py` pin the workflow properties so the suppression cannot come back silently.
