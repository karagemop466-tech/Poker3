### What was concluded from it

1. **The occupancy caveat is closed, not carried.** The earlier trip-window note could not tell whether the
   default read was one or two adults. Requesting the same window with `adults=2` reproduced both averages
   exactly, so the recorded quote is a two-adult quote. Added as a third dated log entry, with the earlier
   entry's caveat rewritten to point at it.
2. **The quote is fee-inclusive, so it cannot enter the cost model.** `Includes Resort Fee` means the $55 is
   already inside $495/$405. The calculator adds the fee itself from a fee-exclusive rate, so typing a Wynn
   average there would charge the fee twice (this is the F69 trap on the Venetian side). `avg × 1.1338` is also
   refused: the page does not state whether the unshown tax is charged on the fee-inclusive average or on a
   fee-exclusive rate, and no checkout total prints. Wynn publishes no room-tax percentage at all (**F39**), so
   Wynn's true nightly cost stays **blank**. The pre-existing derived line (`$405 × 1.1338 = $459.19`,
   `$495 × 1.1338 = $561.23`) is labelled *derived, not quoted*, and is not a checkout total.
3. **Rates moved between windows on the same day, which is why rates are a log.** $654/$564 for a one-night
   stay versus $495/$405 for the seven-night window, read minutes apart. No single "the Wynn rate" value exists
   to store; each dated read is appended (`site/data.json → rateLog`).

## 4. Why the change monitor marked two rows `CHANGED`, and what that means

`site/checks.json` on this branch records `changedCount: 2`, and both rows are Wynn IBE URLs
(`…&checkIn=11/23/2026&checkOut=11/30/2026` and the undated default). Both are marked
`wordingChanged: true` with `hashBasis: visible text (HTML tags, scripts and styles removed)`.

That is the correct reading: a booking engine's visible text differs on **every** request (cart state, session
tokens, offer carousels, `104 purchased in the last 2 days` counters), so a hash over that text changes by
construction. **`CHANGED` on an IBE row is not a venue price change** and must not be treated as one; the
`wordingChanged` flag is what distinguishes it, and the site's rule is unchanged: a detected difference is
published as a mark for a human to re-read, never as an edit to a value (`scripts/check_sources.py` writes only
`site/checks.json` — enforced by `MonitorNeverEditsValues` in `tests/test_monitor_record_robustness.py`).

This is also the class of failure that silenced the monitor: `tests/test_index_evidence_labels.py` used to assert
that the record was dated `2026-11-19` *and* that nothing had changed, inside the gate that precedes the record
commit, so the record of a detected change could never be committed (CI run 44482186623). Fixed on this branch
by making the date assertions relational, reading the landing-page date out of the record instead of hardcoding
it, and publishing the record under `if: always() && !cancelled()`.
